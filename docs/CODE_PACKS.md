# Code packs (custom C#)

A code pack is a BepInEx plugin that registers decor from C#. Reach for it only when you need behavior a
data pack cannot express: a toggle, particles, scripted logic, a response to the player. For everything
else (meshes, materials, textures, placement, price, and animation) prefer a no-code data pack. See
[Creating packs](CREATING_PACKS.md).

A code pack registers items through the same `DecorExpansionAPI` and gets the same permanent IDs as a data
pack, so a pack can start as a data pack and graduate to a code pack later, keeping its `packId` and
`internalName`s, and every item keeps its ID. Players' saves survive the upgrade.

## When you need a code pack

- An item with a light, a particle effect, sound, or physics you drive yourself.
- An item that reacts to the player (a toggle, a proximity effect).
- Any per-item logic beyond the built-in move, rotate, height adjust, and box-up.

If your only goal is a moving prop (a spinning sign, a fan, swimming fish), that is **animation, which is
data**, not code. Ship it as an animated `.glb` in a data pack.

## Requirements

- The **.NET 6 SDK** (`dotnet --version` 6.0 or later).
- A local copy of the player's BepInEx pack DLLs to compile against (Tobey's BepInEx Pack 0.10.0+).
- A `BepInEx/interop/` folder, generated by launching the game once with BepInEx installed.
- The **SuperDecor** framework (`SuperDecor.dll`) to reference.

You compile against these DLLs but never redistribute them. The player already has them.

## 1. Project setup

Create a `net6.0` class library. Reference the framework and the BepInEx pack DLLs with `HintPath`. There
are no NuGet packages for the IL2CPP BepInEx 6 line; reference local DLLs. Point `SuperDecorRefDir` at your
game's `BepInEx` folder.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net6.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <AssemblyName>YourPack</AssemblyName>
    <RootNamespace>YourName.YourPack</RootNamespace>
    <!-- Per-machine path to your local BepInEx folder. Do not commit DLLs. -->
    <SuperDecorRefDir Condition="'$(SuperDecorRefDir)' == ''">/path/to/Supermarket Simulator/BepInEx</SuperDecorRefDir>
  </PropertyGroup>

  <ItemGroup>
    <!-- The framework you call into -->
    <Reference Include="SuperDecor">
      <HintPath>$(SuperDecorRefDir)/plugins/SuperDecor/SuperDecor.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- BepInEx 6 IL2CPP core -->
    <Reference Include="BepInEx.Core">
      <HintPath>$(SuperDecorRefDir)/core/BepInEx.Core.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="BepInEx.Unity.IL2CPP">
      <HintPath>$(SuperDecorRefDir)/core/BepInEx.Unity.IL2CPP.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="BepInEx.Unity.Common">
      <HintPath>$(SuperDecorRefDir)/core/BepInEx.Unity.Common.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- Unity wrappers (unprefixed filenames; only the .NET base library is Il2Cpp*) -->
    <Reference Include="UnityEngine.CoreModule">
      <HintPath>$(SuperDecorRefDir)/interop/UnityEngine.CoreModule.dll</HintPath>
      <Private>false</Private>
    </Reference>

    <!-- Add these two only if your pack ships its own MonoBehaviour -->
    <Reference Include="Il2CppInterop.Runtime">
      <HintPath>$(SuperDecorRefDir)/core/Il2CppInterop.Runtime.dll</HintPath>
      <Private>false</Private>
    </Reference>
    <Reference Include="Il2Cppmscorlib">
      <HintPath>$(SuperDecorRefDir)/interop/Il2Cppmscorlib.dll</HintPath>
      <Private>false</Private>
    </Reference>
  </ItemGroup>
</Project>
```

`<Private>false</Private>` keeps the referenced DLLs out of your build output. The player already has them,
and copying them risks version skew.

## 2. The plugin

The plugin base class is `BasePlugin` (from `BepInEx.Unity.IL2CPP`), and the entry point is `Load()`. There
is no `Awake()`. Log through the `Log` property.

```csharp
using System.Reflection;
using BepInEx;
using BepInEx.Unity.IL2CPP;
using SuperDecor.Api;
using UnityEngine;

[BepInPlugin("com.yourname.yourpack", "Your Pack", "1.0.0")]
[BepInDependency(DecorExpansionAPI.BASE_MOD_GUID, BepInDependency.DependencyFlags.HardDependency)]
public sealed class YourPackPlugin : BasePlugin
{
    public override void Load()
    {
        // Guard for disabled mode (see below). Return early if the framework is not ready.
        if (!DecorExpansionAPI.IsBaseModReady())
        {
            Log.LogWarning($"SuperDecor not ready ({DecorExpansionAPI.GetDisabledReason()}); registering nothing.");
            return;
        }

        // Register the pack FIRST. RegisterDecorItem returns -1 for an unregistered pack.
        bool ok = DecorExpansionAPI.RegisterExpansionPackWithAssembly(
            packId: "com.yourname.yourpack",
            packName: "Your Pack",
            packVersion: "1.0.0",
            author: "Your Name",
            assembly: Assembly.GetExecutingAssembly());
        if (!ok) { Log.LogError("Pack registration failed."); return; }

        int id = DecorExpansionAPI.RegisterDecorItem("com.yourname.yourpack", new DecorItemData
        {
            InternalName = "modern_lamp",     // STABLE, feeds the permanent ID, never rename
            ItemName = "Modern Lamp",
            Description = "A sleek LED floor lamp.",
            Category = DecorCategories.Lighting,
            Price = 180f,
            BaseReferenceID = 2,
            MeshAssetName = "modern_lamp.glb",  // a .glb shipped beside this DLL, or empty for a placeholder
        });

        if (id > 0) Log.LogInfo($"Registered Modern Lamp as {id}.");
        else Log.LogWarning("Could not register Modern Lamp.");
    }
}
```

## 3. Disabled mode

If the framework detects an incompatible game, it runs in a safe disabled mode rather than breaking the
game. The whole API stays loadable, but readiness and registration calls fail quietly and nothing throws.
The only thing your pack must do is guard on `IsBaseModReady()` and return early, as shown above.
`GetDisabledReason()` gives a short reason for logging.

## 4. Live behavior: the spawn hook

To run your own code on a placed item, use the spawn hook. The high-level helper is one line:

```csharp
int id = DecorExpansionAPI.RegisterDecorItem(PackId, new DecorItemData { /* ... */ });
if (id > 0)
    DecorExpansionAPI.RegisterItemBehavior<SpinBehavior>(id);  // attaches SpinBehavior to every placed copy

public sealed class SpinBehavior : MonoBehaviour
{
    public SpinBehavior(IntPtr ptr) : base(ptr) { }            // IL2CPP requires this constructor
    private void Update() => transform.Rotate(0f, 30f * Time.deltaTime, 0f);
}
```

The framework registers `T` once and attaches a fresh instance to every spawned copy of that item. You
never touch Harmony or the IL2CPP class injector. For more control, subscribe to the event and inspect the
instance yourself:

```csharp
DecorExpansionAPI.ItemSpawned += (instance, furnitureId) =>
{
    if (furnitureId != myItemId) return;                       // filter to your item
    instance.AddComponent<MyDriver>();
};
```

Guarantees: the hook fires once per live instance, on every spawn route (initial placement, save-reload,
and the precision-edit swap), after the visual is applied, and fail-soft (a handler that throws is caught
and logged, never breaking the spawn). Attached behaviors die with their `GameObject`.

A pack that ships its own `MonoBehaviour` must reference `Il2CppInterop.Runtime` and `Il2Cppmscorlib`, as
shown in the csproj above.

## Physics props

A code pack can turn a decor item into a physics prop: a Rigidbody object the player can bump and roll. The framework handles the difficult parts, so the pack's contribution is small.

Your behavior (attached with `RegisterItemBehavior<T>`) builds the prop: it swaps in the mesh and adds a collider, a tuned dynamic `Rigidbody`, and a physics material. Put the `Rigidbody` on the **root** of the item so its motion saves and reloads correctly.

For any item that carries a dynamic `Rigidbody`, the framework then does the rest automatically:

- It freezes the prop while you select or place it in Decor Edit Mode and restores its dynamic state afterward, so editing never sends it rolling.
- It captures the prop's rolled position when you select it and when you save, so it never snaps back to where it was first placed.
- It re-supplies the player's push out on the road, where the stock game push is otherwise dropped for low objects.

Two `Rigidbody` settings matter in practice: use `CollisionDetectionMode.ContinuousSpeculative` so a fast prop does not tunnel through the thin road collider, and a `PhysicsMaterialCombine.Average` friction combine so the prop rolls rather than slides. The first-party Orange Physics Ball (in the test pack) is a complete example: it builds only the sphere, collider, material, and `Rigidbody`, and the framework supplies the editing freeze, the road push, and the save/reload.

## IL2CPP rules that bite

These trip up developers coming from the old Mono version of the game:

- **The plugin is not a `MonoBehaviour`.** To run an `Update` loop, attach a `MonoBehaviour` (via the spawn
  hook, or create a `GameObject` and `AddComponent<T>()`). Every injected `MonoBehaviour` needs the
  constructor `public T(IntPtr ptr) : base(ptr) {}`.
- **Field initializers do not run** on an injected `MonoBehaviour` constructed through that `IntPtr`
  constructor. Use `const` or assign in `Start`/`Awake` instead of `private float x = 1f;`.
- **Some Unity value-type constructors are missing.** For example, the framework wraps
  `ParticleSystem.MinMaxCurve` without the `MinMaxCurve(float)` constructor; build a constant curve with a
  small helper (`new ParticleSystem.MinMaxCurve { mode = ParticleSystemCurveMode.Constant, constant = v }`).
- **Log** through `Log.LogInfo` / `LogWarning` / `LogError`. Do not use `Debug.Log` in shipping code.
- **Game types** keep their original names (`IDManager`, `FurnitureSO`) and bind against the wrappers in
  `BepInEx/interop/`, not the original game assemblies.

## Asset loading

A code pack can deliver assets two ways:

1. **A runtime `.glb`** shipped beside your DLL, referenced by `MeshAssetName` (the recommended path, the
   same loader data packs use). The framework builds the mesh, material, textures, and collider.
2. **Embedded resources** under `Resources/{Icons,Meshes,Textures}/`, resolved by the framework when you
   registered the pack with `RegisterExpansionPackWithAssembly`. This is a fallback; prefer runtime glTF.

If no model resolves, the item shows with a box-collider placeholder and is still purchasable and
placeable.

## Complete example: an animated, interactive aquarium

This is the pattern behind the first-party Showcase aquarium. It shows the clean division of labor: the
**fish swim through the model's own animation (no code)**, and only the **light toggle and bubbles** need
this behavior.

The plugin registers the item, turns on the model's `Swim` clip, and attaches the controller:

```csharp
[BepInPlugin(PackId, "SuperDecor Showcase", "1.0.0")]
[BepInDependency(DecorExpansionAPI.BASE_MOD_GUID, BepInDependency.DependencyFlags.HardDependency)]
public sealed class ShowcasePackPlugin : BasePlugin
{
    public const string PackId = "com.leptoon.superdecorshowcase";

    public override void Load()
    {
        if (!DecorExpansionAPI.IsBaseModReady()) { Log.LogError("SuperDecor not ready."); return; }

        DecorExpansionAPI.RegisterExpansionPackWithAssembly(
            PackId, "SuperDecor Showcase", "1.0.0", "Leptoon",
            System.Reflection.Assembly.GetExecutingAssembly());

        int id = DecorExpansionAPI.RegisterDecorItem(PackId, new DecorItemData
        {
            InternalName = "aquarium",            // STABLE, never rename
            ItemName = "Aquarium",
            Description = "A glass aquarium with swimming fish, bubbles, and a light you can toggle.",
            Category = DecorCategories.Fixtures,
            Price = 850f,
            BaseReferenceID = 3,
            MeshAssetName = "aquarium.glb",       // shipped beside the DLL
            // Fish swimming is data, not code: the framework plays the model's "Swim" clip on spawn.
            Animation = new MeshAnimationData { Autoplay = true, Clip = "Swim", Loop = true, Speed = 1f },
        });

        if (id > 0)
            DecorExpansionAPI.RegisterItemBehavior<AquariumController>(id);   // adds the light and bubbles
    }
}
```

The controller adds the light and bubbles and toggles the light on a dedicated key:

```csharp
public sealed class AquariumController : MonoBehaviour
{
    private const KeyCode ToggleKey = KeyCode.L;   // a dedicated key, not the game's interact key
    private const float InteractRange = 4f;

    private Light? _light;
    private bool _on = true;

    public AquariumController(IntPtr ptr) : base(ptr) { }   // IL2CPP requires this constructor

    private void Start()
    {
        var lightGo = new GameObject("AquariumLight");
        lightGo.transform.SetParent(transform, false);
        _light = lightGo.AddComponent<Light>();
        _light.type = LightType.Point;
        _light.range = 3f;
        _light.intensity = 1.8f;
        _light.color = new Color(0.75f, 0.88f, 1f);

        var psGo = new GameObject("AquariumBubbles");
        psGo.transform.SetParent(transform, false);
        var ps = psGo.AddComponent<ParticleSystem>();

        ParticleSystem.MainModule main = ps.main;
        main.loop = true;
        main.startLifetime = Constant(4f);
        main.startSpeed = Constant(0.25f);
        main.startSize = Constant(0.03f);
        main.gravityModifier = Constant(-0.04f);   // gentle upward drift
        main.maxParticles = 60;

        ParticleSystem.EmissionModule emission = ps.emission;
        emission.rateOverTime = Constant(8f);
        ps.Play();
    }

    private void Update()
    {
        if (!Input.GetKeyDown(ToggleKey)) return;
        var cam = Camera.main;
        if (cam == null) return;
        if (Vector3.Distance(cam.transform.position, transform.position) > InteractRange) return;
        _on = !_on;
        if (_light != null) _light.enabled = _on;
    }

    // The framework wraps MinMaxCurve without a float constructor, so build a constant curve by hand.
    private static ParticleSystem.MinMaxCurve Constant(float value)
    {
        var c = new ParticleSystem.MinMaxCurve();
        c.mode = ParticleSystemCurveMode.Constant;
        c.constant = value;
        return c;
    }
}
```

Notes: the light toggle reads a dedicated key (`L`) rather than the game's interact prompt, because the
interact key is used by the built-in move and rotate. A shipping pack would expose the key and the light
color through a BepInEx config so players can change them.

## Build, deploy, test

1. `dotnet build -c Release` produces `YourPack.dll`.
2. Copy it into `<game>/BepInEx/plugins/` (its own subfolder is fine), along with any `.glb` it references.
3. Launch the game. Watch `<game>/BepInEx/LogOutput.log` for your plugin's lines.
4. Open the in-game computer, open the SuperDecor Shop, then purchase and place your item.

## Troubleshooting

- **Item does not appear:** confirm the framework loaded first, your pack registered (no `-1` returns),
  every `internalName` is unique, and the model path resolves. Check `BepInEx/LogOutput.log`.
- **`RegisterDecorItem` returns -1:** the pack was not registered first, or `InternalName` is empty.
- **IDs shifted between versions:** you renamed `packId` or an `internalName`. Revert. Those two are
  permanent.
- **Wrong or missing model:** a missing model is not fatal; the item shows with a placeholder. Confirm the
  `.glb` sits beside the DLL.
